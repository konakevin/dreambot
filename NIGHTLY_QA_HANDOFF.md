## What we're actually building (read this first)

We are NOT trying to make Hawaii dreams good in isolation. We are building a **reproducible production pipeline** so that any location a user picks in onboarding (Hawaii, Bali, Paris, Iceland, Tokyo, …) reliably produces lush, on-brand, location-recognizable dreams — with **zero engine re-design per location**.

**Hawaii is the test bench, not the destination.** It's the location we're using to calibrate the engine. Every QA round we run on Hawaii (R32, R33, R34, R35…) is shaking out brittleness in the *engine*: the brief, the L/R lock, the action pool, the composition paths, the cull script, the dream-eligible curation. The Hawaii images are the side effect. The hardened engine is the deliverable.

**The artifacts ARE the reproducible pattern.** When we say "reproducible," we mean these specific artifacts, working together, can be applied to a new location with no code change beyond (potentially) adding a new biome config:

- `_shared/biomeAxes.ts` — atmosphere library (one config per biome, reusable across locations)
- `scripts/gen-location-hints.js` — Stage 1 of the per-location pipeline (sub-regions + must-include categories)
- `scripts/gen-iconic-spots-50.js` — Stage 2 (named-landmark pillars, biome-aware)
- `scripts/qa-nightly-scene.js` — render-test loop
- `scripts/_cull-action-pools.mjs` — pose-pool safety cull
- `nightly-dreams/index.ts` brief construction — reads biome + pillars at render time
- The `is_dream_eligible` curation on mediums + vibes
- The `quality_tier` system on iconic spots (S/A/B)

Once the engine is locked, fan-out is mechanical: pick the biome, run Stage 1, run Stage 2, render-test, tier the pillars, ship. **No engine re-design. No bespoke code per location.** The bespoke part is the data (each location's biome assignment, hints, pillars) — the pattern around it is uniform.

**Each location gets its own bespoke instantiation of the same recipe:**
- Its own **flavor** entry in `scripts/locationFlavor.js` — pool size + a 1-2 sentence "soul" + a list of required iconic anchors + emphasis split + de-emphasize warnings. This is the LOCATION IDENTITY that Stages 1 / 2 / 2b all read so their Sonnet prompts produce specific-not-generic output.
- Its own **hints** (sub-regions to cover + must-include feature categories), generated by Sonnet in Stage 1, persisted on `location_cards.sub_regions` + `location_cards.must_include`.
- Its own **iconic pillars** (50-250 named-landmark anchors depending on location breadth), generated by Sonnet in Stage 2 from the hints, stored in `location_iconic_spots`.
- Its own **bespoke `biome_config`** (Stage 2b — added 2026-05) — a per-location BiomeConfig JSON authored by Sonnet, stored on `location_cards.biome_config` (JSONB, migration 170). This OVERRIDES the shared `biomeAxes.ts` lookup at render time so every TIME / WEATHER / PHENOMENA entry is recognizable to anyone who has been there. "Diamond Head sunrise" for Hawaii. "Tunnel View golden hour on El Capitan" for Yosemite. "Shibuya rain-slick midnight" for Tokyo. NOT generic "alpine sunset" / "urban night".

**Why bespoke biomes matter (this is the core quality lever):**

The shared `biomeAxes.ts` library has ~6 categorical biomes (tropical_coastal, arctic_polar, ancient_ruins, scifi_cosmic, fantasy_imagined, gothic_historic). They're good FALLBACKS but they cannot deliver location-specific atmospheric DNA. Two locations sharing `alpine_mountain` would feel identical: Yosemite would lose its Half Dome / El Capitan / Bridalveil Falls / Horsetail firefall identity; Swiss Alps would lose its Matterhorn / Eiger / Jungfrau identity. A user who has been to Yosemite seeing a generic "alpine sunset" dream would not feel "yes, that's MY location" — they'd just see a mountain dream.

A bespoke `biome_config` for Yosemite has TIME entries like "Valley View pre-dawn — first alpenglow igniting Half Dome's northwest face while Bridalveil Fall remains in deep shadow, Merced River perfectly still". PHENOMENA entries like "Horsetail Fall firefall — mid-to-late February sunset igniting the 1,000-foot waterfall in molten orange-red light". Anyone who has been to Yosemite reads those and says "yes, that IS Yosemite." THAT is the quality bar we are shipping to.

Same workflow shape every location, different content. The flavor module + bespoke biome + iconic pillars are the three layers of customization that make every location feel like itself.

## The reproducible per-location workflow (the playbook)

### Stage 0 — Set up the row + decide fallback biome

1. Insert `location_cards` row with `name` (lowercase), `display_name`, `picker_category`, `picker_sort_order`, `is_approved=true`.
2. Optionally set `location_cards.biome` to a shared biome key as a **fallback** (in case Stage 2b is skipped or its config is invalid). Pick from these:

| Picker category | Biome (current or proposed) | Notes |
|---|---|---|
| `tropical` | `tropical_coastal` (current) | Hawaii is the proof. Maldives, Bali, Caribbean likely fit; Bali jungle interior may need split. |
| `iconic_cities` | `urban_modern` / `urban_historic` (proposed split) | Dubai/HK/Tokyo are modern; Paris/Rome/Venice are historic. Atmospheric vocab differs. |
| `epic_nature` | `mountain_alpine`, `temperate_forest`, `jungle` (proposed) | Canadian Rockies vs Amazon are very different — separate biomes. |
| `ancient` | `ancient_ruins` (current) | Already in use for "Ancient Wonders" meta-location. |
| `gothic` | `gothic_historic` (proposed) | Victorian London. Could inherit `urban_historic` + vibe lean if minimal. |
| `fantasy` | `fantasy_imagined` (current) | Allows magical realism, glowing details, impossible beauty. |
| `scifi` | `scifi_cosmic` (current) | Allows alien skies, twin moons, megastructures. |
| (arctic, desert) | `arctic_polar` (defined, dormant), `desert` (proposed) | Iceland is the only `arctic_polar` location today. |

**When to add a NEW biome (vs reuse an existing one):**
- Existing biome's TIME / WEATHER / PHENOMENA vocabulary doesn't fit the location's reality (e.g., "tropical sunset on water" is wrong for Paris)
- Existing biome's BANS conflict with location (e.g., `ancient_ruins` bans modern infrastructure — wrong for a contemporary city)
- Existing biome's SUBJECT_RULE doesn't describe what the location IS (e.g., "iconic ancient monument as the hero" is wrong for Hawaii)

If 2/3 of the above are true → new biome. Otherwise reuse.

**NOTE:** Since Stage 2b (bespoke biome) was added, the shared biome only matters as a fallback. Setting `biome` is still recommended (some Stage 1 / 2 prompts use it as a hint for source-canon vs real-Earth branching), but the actual atmosphere at render time will come from `biome_config` once Stage 2b runs.

### Stage 0b — Add the flavor entry (CRITICAL — do not skip)

Open `scripts/locationFlavor.js` and add an entry for the location. Minimal:

```js
'<name>': { count: <50-250> }
```

Full version (recommended for region metas, country-scale locations, or anything with a distinct cultural identity):

```js
'<name>': {
  count: <50-250>,                                  // Stage 2 pool size
  soul: '1-2 sentences describing what this location IS',
  anchors: ['Top iconic landmark 1', 'Top iconic landmark 2', ...],
  emphasis: '40% A, 30% B, 20% C, 10% D — rough split of pillar categories',
  deemphasize: 'optional — what to AVOID over-indexing on (e.g. "minimize coastal" for China)',
}
```

**Pool size guide** (Kevin's rule, documented 2026-05):
- 200-250: massive country meta with multi-region scope (China, India)
- 150-200: large country (Australia, Mexico, Turkey, Thailand)
- 100-150: continent-scale wilderness (Amazon, NZ, Iceland)
- 75-100: signature single region (Yellowstone, Patagonia, Norwegian Fjords, Bali)
- 50-90: cities (range from compact like Singapore at 50 to dense like Paris at 90)
- 50: narrow whimsy (Fairy Cottage, Princess Garden Castle)

The flavor entry is the source of truth for the location's identity — Stage 1, Stage 2, and Stage 2b all read it via `flavorBlock(loc)` and inject it into their Sonnet prompts. Junk flavor → junk output across all three stages.

### Stage 1 — Generate hints

```bash
node scripts/gen-location-hints.js --location <name>
```

What it does: Sonnet (claude-sonnet-4-5) enumerates for that location:
- **`sub_regions[]`** — distinct geographic / thematic sub-areas to spread coverage across (e.g., for Hawaii: 22 entries spanning all islands and coast types — Oahu South Shore, Maui Hāna Coast, Big Island Volcano, Kauai Nā Pali, etc.)
- **`must_include[]`** — feature categories the pillar pool MUST contain (e.g., for Hawaii: named beaches, surf spots, snorkel reefs, waterfalls, valleys/canyons, volcanic features, iconic hikes, lookouts)

Persists to `location_cards.sub_regions` and `location_cards.must_include` (added by migration `164_location_hints.sql`).

Biome-aware: fantasy locations get fictional canon, sci-fi gets world-building lore, real-world gets actual geography.

**Review step:** open the row in Supabase and read sub_regions + must_include. If Sonnet missed obvious sub-regions, hand-edit the array. This file is the brief for Stage 2 — junk in, junk out.

### Stage 2 — Generate pillars

```bash
node scripts/gen-iconic-spots-50.js --location <name>          # writes to DB at tier 'A'
node scripts/gen-iconic-spots-50.js --location <name> --dry-run # preview only
```

What it does: reads the location's biome + sub_regions + must_include. Picks a meta-prompt variant based on biome:
- **Real locations** — hard rules: 4-10 words, named landmarks only, outdoor/exterior, no time/weather/light/people/interiors/industrial/hallucinations. Must spread across all sub_regions, must cover all must_include categories.
- **Fantasy biomes** — 4-12 words, named fictional canon landmarks (Hogwarts has Astronomy Tower, Forbidden Forest, etc.), exterior view of interior-iconic places.
- **Sci-fi biomes** — 4-12 words, named sci-fi canon landmarks, alien skies / megastructures fair game.

Inserts at `quality_tier='A'` by default. Existing `'S'` tier entries are preserved (the hand-locked banger pillars).

**As of 2026-05 the runtime no longer filters on `quality_tier` (the grader was too strict — it demoted legit Hawaii postcards like Hapuna Beach to B). All active pillars are eligible at render time.** S/A/B labels remain in the DB as historical signal — useful if you want to revisit the grader rubric or hand-promote favorites later. To re-enable tier-based gating, add `.in('quality_tier', [...])` back to the iconic_spots query in `nightly-dreams/index.ts:746`.

### Stage 2b — Author the bespoke biome config

```bash
node scripts/gen-location-biome.js --location <name>          # writes to DB
node scripts/gen-location-biome.js --location <name> --dry-run # preview only
node scripts/gen-location-biome.js --all                       # batch (skips locations already configured)
```

What it does: Sonnet (claude-sonnet-4-5) reads the location's flavor (soul + anchors), Stage 1 hints (sub_regions + must_include), and picker category. Outputs a `BiomeConfig` JSON object with location-specific:
- **TIME** (8 entries) — time-of-day descriptors grounded in the location's signature atmospheric DNA
- **WEATHER** (7 entries) — weather conditions specific to the location's climate vocabulary
- **CAMERA** (5 entries) — cinematic framings appropriate to the location's scale
- **PHENOMENA** (12 entries) — atmospheric / light / natural phenomena unique to this place
- **SUBJECT_RULE** (1 paragraph) — what the render subject IS for this location
- **BANS** (6-8 entries) — location-aware hard rules (NO snow in Hawaii, NO palm trees in Yosemite, etc.)

Persists to `location_cards.biome_config` (JSONB, migration 170).

**The prompt strictly forbids people-as-atmosphere** — even iconic crowd-density places (Shibuya scramble, Times Square) must be rendered EMPTY (off-hours / pre-dawn / etc.). This is because the nightly engine's biome axes drive scene-only renders, not character renders. If you allow "thousands flowing across the crossing", you get a NO-PEOPLE bans collision and the render breaks.

**Quality bar**: every TIME / WEATHER / PHENOMENA entry must be SPECIFIC to this location. A traveler who has been there should recognize each one. Generic atmospheric language is a fail. Always run `--dry-run` and read the output for the first ~5 locations you generate to verify the bar is being met; tighten the meta-prompt in `scripts/gen-location-biome.js:buildPrompt()` if outputs feel generic.

**Runtime preference order** (`nightly-dreams/index.ts:756`):
1. `location_cards.biome_config` if set + shape-valid (bespoke wins)
2. `getBiomeConfig(location_cards.biome)` lookup in `biomeAxes.ts` (shared fallback)
3. `getBiomeConfig(null)` returns `tropical_coastal` (universal default)

Re-running gen-location-biome with `--location X` SKIPS if the row already has a biome_config (intentional — preserves manual edits). To regen, clear the column first: `UPDATE location_cards SET biome_config = NULL WHERE name = '<name>';`.

### Stage 3 — Render-test and tier

QA loop runner:
```bash
# Scene-only batch
node scripts/qa-nightly-scene.js --round N --count 5 --cast none --location <name>
# Single character batch
node scripts/qa-nightly-scene.js --round N --count 5 --cast single --location <name>
# Dual character batch (only relevant if user has plus_one)
node scripts/qa-nightly-scene.js --round N --count 5 --cast dual --location <name>
```

Each render gets caption-tagged `auto-qa: nightly-scene R<N>` so you can filter the feed.

**Tier the pillars based on render output:**

```sql
-- Promote a banger to S-tier (always picked first)
UPDATE location_iconic_spots
SET quality_tier = 'S'
WHERE location_key = '<name>' AND spot_text = '<exact text>';

-- Demote a bad pillar to B-tier (excluded at render time — engine only picks S/A)
UPDATE location_iconic_spots
SET quality_tier = 'B'
WHERE location_key = '<name>' AND spot_text = '<exact text>';

-- Or set is_active=false to fully hide
UPDATE location_iconic_spots
SET is_active = false
WHERE location_key = '<name>' AND spot_text = '<exact text>';
```

The render-time query in `nightly-dreams/index.ts:660-664` filters `is_active=true` and `quality_tier IN ('S','A')`.

Run 5-10 renders per cast mode per location. If a pillar consistently produces beautiful renders, promote to S. If a pillar consistently produces broken/ugly/unrecognizable renders, demote to B. Don't grade individual renders against the engine — grade the PILLARS.

### Stage 4 — Ship

When the location's renders are consistently A+ across all 3 cast modes (scene/single/dual), the location is shipped. Move to the next.

## Architecture: how the three components feed the prompt

At render time, `nightly-dreams/index.ts` does this:

```
user.places[0]                          ─→ name (e.g., 'hawaii')
  │
  ├─→ location_cards.biome_config       ─→ bespoke BiomeConfig (PREFERRED)
  │   └─→ pickAxis() rolls one TIME, WEATHER, CAMERA, PHENOMENON
  │       (location-specific entries — "Diamond Head sunrise", etc.)
  │
  ├─→ location_cards.biome              ─→ 'tropical_coastal' (FALLBACK)
  │   └─→ BIOME_AXES['tropical_coastal']
  │       └─→ pickAxis() rolls one TIME, WEATHER, CAMERA, PHENOMENON
  │       (generic categorical entries — used only when biome_config is NULL)
  │
  └─→ location_iconic_spots             ─→ random active pillar
      └─→ "Nā Pali Coast emerald cliffs and Pacific surf"
```

That feeds two branches based on cast mode:

**Scene-only branch** (`pure_scene`, ~L876):
- Pillar = LOCKED SUBJECT
- Biome SUBJECT_RULE describes what the subject IS
- Biome BANS go in as hard guardrails
- Rolled axes apply atmosphere (light/weather/framing) ONLY — never alter the subject

**Character branch** (`character`, ~L688):
- Pillar = LOCKED BACKDROP
- Same axes apply atmospheric conditions to the backdrop
- Cast members dominate the foreground; backdrop is recognizable but not hero
- Face-swap eligibility triggers FACE_SWAP_FLUX_OVERRIDES + L/R lock + action pool injection

**Hierarchy when sources conflict in the brief:**
1. Biome BANS (highest — hard rejects)
2. Pillar text (locked subject/backdrop — Sonnet must NAME it explicitly in the prompt)
3. Composition prepend (early-token weighting — cinematography signal)
4. Sonnet-written body (medium / scene description / character description)
5. Rolled axes (light, weather, phenomena — modifiers, not subjects)

The pillar always wins on identity. The composition prepend always wins on framing. When those two are aligned, the brief produces good renders. When they conflict (see R34's `intimate` failure), the prepend's framing wins because it's first in the prompt, defeating the brief.

## Stream 2 — Dual character face swap reliability

This is the active failure surface as of R34. Goal: dual face swaps consistently land both faces on the right bodies, no gender swaps, no extreme close-ups, no asymmetric poses.

### The 7-layer dual pipeline (defense in depth)

| # | Layer | Where | Role |
|---|---|---|---|
| 1 | Composition path prepend | `_shared/pools/dual_composition.ts` | Cinematography preset injected at start of Flux prompt |
| 2 | Action pool | `_shared/pools/dual_actions.ts` | Body language for BOTH characters |
| 3 | Flux fragment override | `FACE_SWAP_FLUX_OVERRIDES` in nightly-dreams | Runtime override of medium's flux fragment |
| 4 | Directive override | Same record | Style guide Sonnet reads |
| 5 | Sonnet brief | `nightly-dreams/index.ts:~657` | Structured prompt instructions |
| 6 | Post-processing prepend | `nightly-dreams/index.ts:~870` | Composition prepend prepended after Sonnet writes |
| 7 | dualFaceSwap execution | `_shared/faceSwap.ts:439` | Crop L 55% → swap → crop R 55% → swap → stitch |

### L/R role lock (SHIPPED, defense in depth at 3 layers)

The fundamental promise: **self → LEFT half, plus_one → RIGHT half, deterministic regardless of render output**.

- **Algorithm** (`dreamAlgorithm.ts:122`): `castMembers = [selfMember, plusOne]` — self always index 0
- **Brief** (`nightly-dreams/index.ts:694`): "ROLE-TO-SIDE LOCK" section explicit in Sonnet brief
- **Pipeline** (`nightly-dreams/index.ts:1015-1026` + `faceSwap.ts:439`): `dualFaceSwap(leftSourceUrl=self.thumb, rightSourceUrl=plus_one.thumb)`

Even if Sonnet/Flux mis-render the side, the swap is deterministic.

### Action pool tier strategy

| Tier | Count | Construction | Use |
|---|---|---|---|
| **S-tier** | 33 | Manual hand-cut. Every entry leads with "both" + matched-stance verb. Not currently in use. | Fallback if A-tier produces too many regressions. |
| **A-tier** | 224 (90 COMPANION + 134 PARTNER) | Script-passed (rejects asymmetric, face-away, motion, head-down). Currently active. | Default. More variety. |

`pickDualAction()` rolls 30% PARTNER pool / 70% COMPANION pool when relationship is partner/significant_other. Otherwise always COMPANION.

**Known regex gaps in cull script** (from R34 #5 analysis):
- "drinking from bottle" / "tucking into belt" / similar head-occluding actions pass the script
- Could tighten regex OR fall back to S-tier (sidesteps the class)
